# cfg-lab Secrets Inventory

Authoritative list of every credential the `cfg-lab` Hyper-V lab (and its
controller/steward fleet) depends on: where each one lives today, how it got
there, and the exact recovery step if it is lost or the host holding it dies.

**Why this doc exists.** The 2026-07-31/08-01 full lab rebuild (see
[`controller-ha-real-cluster-runbook.md`](../testing/controller-ha-real-cluster-runbook.md#1-environment)
"Lab rebuild note") happened because the secrets needed to recover the lab were
never captured anywhere durable — they existed only as plaintext files or
in-process state on one host. When that host's steward wedged, there was no way
back in short of rebuilding the controller, regenerating its CA, and
re-enrolling the entire fleet. This doc is the fix: one place that says what
exists, where it lives, and how to get it back.

**Operating rule going forward:** every credential generated by a lab bootstrap
script must be captured into an OS keychain (see each script's own one-time
print instructions) **and** added to the table below in the same change. A
secret that exists only on one host's disk is one bad day away from another
full rebuild.

## 2. Immediate gaps to close

As of this writing, only two of the seven lab-critical secrets above are
actually in a keychain (`cfgms-lab-datasvc-minio`, `cfgms-lab-datasvc-postgres`
— verified via `cmdkey /list` on `CFG-70-02`). Three concrete gaps:

1. **Session HMAC key and SSH private key are capturable right now** — both are
   short values that fit `cmdkey`'s generic-credential size limit. See §3 for
   the exact commands.
2. **The admin bundle has no Windows path at all.** `scripts/cfgms-bundle-load`
   and [`tier1-controller-bringup.md`](tier1-controller-bringup.md) §5 only
   document Linux (`secret-tool`) and macOS (`security`) — there is no Windows
   equivalent, which is *why* `admin.bundle.yaml` has sat as a permanent
   plaintext file on `CFG-70-02` since the rebuild: the documented procedure
   physically cannot be followed on this host's OS. At 4.7KB, the bundle is
   also too large for a single `cmdkey` generic-credential value (practical
   limit is roughly 2.5KB). This needs either a Windows DPAPI-backed storage
   mechanism (e.g. `ConvertTo-SecureString`/`Export-Clixml`, which encrypts to
   the current user+machine) or a chunked `cmdkey` scheme, plus a
   `cfgms-bundle-load`-equivalent that can read it back. **Filed as a gap, not
   fixed in this pass** — the story that adds it should also teach
   `cfgms-bundle-load` to detect Windows instead of hard-refusing.
3. **The OpenBao unseal key and root token** (minted during #3130's live
   execution) must be captured into Credential Manager the moment they are
   printed — they are never re-printed on a later run.

## 3. Windows Credential Manager reference

`cmdkey` can **store** and **list** generic credentials but cannot **print** a
stored password back out — reading a value back requires PowerShell:

```powershell
# Store (one-time, when a script prints a new secret)
cmdkey /generic:cfgms-lab-ssh-key /user:cfgms_lab_ed25519 /pass:"<paste private key contents>"

# List what's stored (values never shown)
cmdkey /list

# Read a stored value back
$cred = Get-StoredCredential -Target 'cfgms-lab-datasvc-postgres'   # requires the CredentialManager PS module
# or, without extra modules, via the Win32 CredRead API:
Add-Type -AssemblyName System.Runtime.InteropServices
# (see scripts/ha-cluster-node-bootstrap.sh's OS-keychain guidance for the equivalent Linux/macOS commands)
```

Until the `cfgms-bundle-load` Windows gap (§2 item 2) is closed, treat
`cmdkey /generic:<target> /user:<label> /pass:<value>` as the store step and
plan on a manual PowerShell `CredentialManager` module read (`Install-Module
CredentialManager`) to retrieve values — there is no equivalent of
`cfgms-bundle-load` yet for this host.

## 4. Recovery checklist (start here after any "lab is unreachable" incident)

1. Check this doc — is the failure a lost secret, or something else (network,
   VM powered off, steward crashed)? Don't assume secrets are lost; verify
   first (`cfg steward list`, `ssh debian@<host>`, controller `/api/v1/health`).
2. If a *specific* secret is confirmed lost, find it in §1's table and follow
   its "Recovery if lost" column — most are recoverable without a full rebuild.
3. If **multiple** interlocking secrets are lost simultaneously (the admin
   bundle *and* the controller CA, or the OpenBao unseal key with no other
   share), a full rebuild following
   [`controller-ha-real-cluster-runbook.md`](../testing/controller-ha-real-cluster-runbook.md)
   and [`tier1-controller-bringup.md`](tier1-controller-bringup.md) is the only
   path — budget for it accordingly and capture every newly-generated secret
   into Credential Manager *before* moving on to the next step this time.
