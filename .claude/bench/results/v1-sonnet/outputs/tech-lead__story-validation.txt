1. **No measurable baseline or target.** "Sync is faster" and "Users are happy with the performance" are not verifiable acceptance criteria. An agent cannot determine when it's done without a concrete metric (e.g., "p99 sync latency under 200ms", "reduce sync time by X%", "benchmark shows Y improvement").

2. **No specific scope.** "The sync code" does not identify any file, package, or function. The agent cannot start work without at least a package path (e.g., `features/sync/`, `pkg/controlplane/`), a function name, or a concrete code reference.

3. **Ambiguous dependency.** "The caching work" is not linked to a specific story or issue number. The agent cannot verify whether this prerequisite has landed or identify what interface/API the caching work exposes.

4. **AC is not independently verifiable.** "Add some tests" is not a testable acceptance criterion — it specifies no behavior under test, no package, no coverage threshold, and no test type (unit, integration, E2E).

5. **No implementation approach.** There is no description of *how* to improve performance — no algorithmic change, no caching strategy, no batching approach, no profiling data. An agent would have to make an arbitrary technical choice with no story guidance.

6. **No definition of "sync".** The story does not specify which sync path is slow (DNA sync, config inheritance resolution, steward pull, controller push, etc.), making the scope entirely ambiguous.
